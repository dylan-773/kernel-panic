Before this agent's first turn on the craft-station brief, `pipeline/proposals/ux-agent.json` still held the prior cycle's items (patch-pouch-strip, patch-ghost-preview, patch-craft-flow, darknet-window, result-drop-reveal, boost-bays). That file was the clearest available example of the expected density for this role, so its conventions were carried forward:

- **Cite exact existing CSS classes and, where known, line numbers** for every reused piece of chrome (e.g. "reuse `.kp-dweld` (styles.css:3487, duel-board.tsx:133)") rather than describing a visual in the abstract. This lets the Orchestrator implement without re-deriving which primitive to reuse.
- **Name every new class/keyframe explicitly** and say plainly when something can and cannot reuse an existing keyframe (see [[feel-decisions-craft-station]] on the `kp-legal-pulse` stroke-vs-border-color trap).
- **Write acceptance checks as falsifiable, observable claims**, not vibes ("feels better" is never acceptable; "the chip returns to its exact origin slot" is).
- **One ui-spec item can be very long and cover multiple sub-surfaces** (a window plus the screen it partially replaces) as long as it stays one coherent deliverable named by the brief; splitting it into many small items is not required or expected when the brief scopes "one ui-spec."
- Each proposal's top-level `notes` field is where the running rationale, reused-idiom list, and Tutorial Agent teaching flags go; keep it dense but do not duplicate detail already stated inside an item's own `spec` field, since the Tutorial Agent gate is more likely to read the item's own text than the file-level notes.
- **When an item needs a genuinely new engine primitive** (a reducer field, a new WindowManager method, a component-state transcript that did not exist before), **name it plainly inside that item's own `spec` text and say explicitly that it is not a balance/mechanics change** if it touches no win-rate/cost/curve number — e.g. "DuelFinish and lastResult gain a `log:string[]` field... a presentational field no win/loss/payout math reads." This lets the Orchestrator budget the hook and lets the balance-loop gate see at a glance that it does not apply.
- **Name a reused structural pattern explicitly when a new item repeats it**, rather than re-deriving the same reasoning from scratch — e.g. "matching the pouch-card-to-SOLDER.BAY precedent already established (one shop surface's old affordance becomes another surface's signpost)" when NIGHT.SYS's BUY BLIND button became a redirect to DARKNET.LNK instead of its own inline purchase action. Precedents named once are cheap to cite again and keep later proposals internally consistent without re-litigating.

Also confirmed operationally, TWICE NOW across two separate cycles (craft-station, then ui-integration-2026-07-29): `pipeline/proposals/<agent>.json` is the SINGLE current-cycle file per agent, entirely replaced each cycle (not appended to), and a coordinator has had to interrupt this agent BOTH times to point out the file on disk still held the prior cycle's content after a long research pass. The fix that actually works is procedural, not just "remember to write eventually": treat the Write call as part of the SAME turn as the research, not a follow-up — draft the item list mentally (or in a scratch note) only long enough to keep momentum, then write the full envelope to disk before doing anything else, and re-write it again (fully replacing) if more items get added later in the same turn. Do not treat research/drafting as done until the file on disk reflects it; a very long grounding pass is exactly the condition under which this mistake recurs, so treat "the research is getting long" as the cue to write a first complete draft now rather than a reason to keep reading.
