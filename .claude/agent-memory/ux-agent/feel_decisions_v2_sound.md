Decisions and corrections from the v2 sound design pass (`pipeline/proposals/ux-agent.json`), kept because the framework and the technical correction both generalize past this one cycle.

- **sfxr's `arpMod`/`arpSpeed` gives exactly ONE pitch jump per note, not a multi-step staircase.** Reading `sfxr.ts`'s `renderSfxr` closely: `arpLimit` is zeroed the instant it fires (`if (arpLimit !== 0 && ++arpTime >= arpLimit) { arpLimit = 0; fperiod *= arpMod; }`), so a preset can only ever produce a single mid-note "chirp up/down", never a repeating staircase. A TRUE multi-step sequence (matching a visual `steps(4)` or a cascade of claims) has to be built by the CALLING CODE invoking one short preset several times at different `rate` values with small delays between calls, exactly how `playCascade` already does it. **Why:** I initially assumed arpMod could represent "4 discrete steps" directly on a single preset to literally mirror a CSS `steps(4)` transition, which is wrong and would have shipped a spec the engine can't produce. **How to apply:** before writing any preset param object that's supposed to feel "stepped" across more than one jump, check whether the calling code needs a small composite function (playCascade's pattern: N calls to one preset at staggered `rate`/`at`) rather than reaching for arpMod alone; arpMod/freqSlide together on a single preset is fine for a two-part "chirp then settle" gesture, but not for anything that needs to visibly count multiple beats.

- **A 4-register wave-family framework, mapped by waveform the way the visual system maps role to hue, now governs this game's whole sfx palette and should be the starting lens for any future preset.** Wave 0 (square) = the CORE VOICE, every routine chrome/commit (open, close, press, confirm, cast, claim). Wave 1 (saw) = FRICTION (refusal, denial, and specifically the machine's own casts). Wave 2 (sine) = the SOFT register, used two ways: gentle pre-commit/advisory feedback (hover, tick, page of prose) OR, when shaped with punch+arp, a warm organic/material register (a weld fusing, a heartbeat, strain healing) — but never a hard commit on its own. Wave 3 (noise) = IMPACT, reserved for genuine physical contact (sparks, traps, paper, breaking). A fifth informal register (`granted`/`unlock`) is the one shared REWARD voice reused for every flavor of "you gained something" regardless of context. **Why:** auditing all 40 shipped presets against this framework found the existing palette ALREADY embodies it almost perfectly (38 of 40 needed zero param changes) — it was implicit good instinct from earlier passes; making it explicit is what let this cycle judge new presets and the one real bug (see below) with a stated rule instead of vibes. **How to apply:** when a brief asks for a new sfx preset, name which of the 4 registers (or the reward-voice exception) it belongs to before choosing wave/params; if it doesn't fit any cleanly, that's a signal to reconsider the design rather than invent a 5th register casually.

- **PHASER (`phaserOffset`/`phaserSweep`) is the intrusion's fingerprint and should never appear on a player-caused or shop-chrome cue.** Paired with a downward `freqSlide` on saw or noise, it marks either the machine casting an ability (`redirect`, `overloadCast`, `virusSting`) or the board itself rupturing regardless of whose action caused it (`trapFire` — a trap springing is treated as a third, neutral "board rupture" category, not a violation of the rule). Vibrato (`vibDepth`/`vibSpeed`) is shared more freely and is NOT reserved the same way: alone, without phaser and a downward slide, it just reads as searching or uncertain (`scanCast`'s sweep, `darknetReveal`'s blind-pull wobble), not hostile. **Why:** this distinction lets a future preset use vibrato freely for "uncertain/searching" moments while still keeping the machine's specific glitch identity legible and exclusive, matching the visual rule that the intrusion is a support-tone-plus-glitch-motion identity, never a second hue. **How to apply:** before adding phaser to any new preset, confirm the triggering actor is the machine/intrusion or a neutral board rupture; if it's the player or shop chrome, drop the phaser and keep any vibrato undramatic (no paired downward slide).

- **Frequency of repetition alone does not determine loudness tier; only PASSIVE/incidental repetition does.** `rotate` and `press` fire constantly during play yet correctly stay at full "chrome" volume (0.4+) because they are the player's own deliberate primary input — players want to feel every one of their own actions land, repetition doesn't cheapen that. Cues that repeat passively (window refocus clicks across a stack, BUS.LOG's own ambient log-line arrivals, drag-hover crossings) correctly sit much quieter (0.14-0.34) since they are incidental feedback, not the main event. **Why:** a naive "reduce volume for anything that repeats" rule would have wrongly demoted the game's core input feedback. **How to apply:** when setting a new cue's volume, ask whether the repetition is the player's own primary verb (keep loud) or ambient/incidental noise around it (go quiet), not just how many times per minute it fires.

- **A generic catch-all preset shared across many unrelated call sites (`icon`, borrowed 12+ times across shop-os.tsx plus teach.tsx) is a smell worth auditing for redundant double-fires, not just a "needs more variety" problem.** Tracing `icon`'s call sites found it was firing ALONGSIDE `winOpen` on every single desktop-icon window open, since `FloatingWindow`'s own mount effect (`wm.tsx`) already voices every window open independently of whatever preceded the click that caused it. The fix wasn't "give icon more friends", it was centralizing the window-open/close voice in the ONE component that owns that lifecycle (`FloatingWindow`, adding a symmetric unmount cleanup) and removing every redundant call that had been firing at the trigger site. **Why:** redundant sound at adjacent trigger points reads as mud, not richness, and is easy to miss without tracing what ELSE fires as a side effect of the same state change. **How to apply:** when a preset is reused at many call sites for "roughly the same kind of thing", check whether any of those call sites also cause a SEPARATE component's own lifecycle effect to fire its own sound for the same event, before assuming the fix is retuning or splitting the preset.
