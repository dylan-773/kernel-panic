Decisions made while speccing `solder-bay-window` (`pipeline/proposals/ux-agent.json`), kept here because the reasoning generalizes past this one window.

- **Defer the reducer dispatch until the animation's payoff frame lands, not the input event.** For a synchronous, instant reducer action (craftPatch has no server round trip), firing dispatch immediately on drop makes React re-render the shrunk array before the visual "weld" has played, which reads as the state changing ahead of the feedback. Fix: run a purely local/transient overlay (spark + merging glyphs) from t=0, dispatch the real action only when that overlay's "WELD" phase completes (t=260ms in the SOLDER.BAY timeline), then let the real re-render (kp-slot-in stagger) carry the "REVEAL" phase. **Why:** state should never visibly change before the sound/motion that explains it lands. **How to apply:** any future payoff-beat spec wrapping a synchronous, instant reducer action (crafting, salvaging, discarding) should default to this "local overlay first, dispatch at the emphasis beat, let the real re-render carry the settle" structure rather than dispatching on the raw input event.

- **Screen-shake tiers (kp-shake-1/2/3) are dive-scale by default; scope them narrower for desktop-side payoffs.** The existing tiers apply to `.kp-dive2` (the whole duel screen) for in-duel impacts. Reusing the same CLASS (not inventing a new keyframe) but applying it to a small purpose-built wrapper (`kp-solder-deck`, just the rack/worktop) keeps a satisfying "thunk" without shaking window chrome or the desktop, which would read as disproportionate for a free, mechanics-neutral crafting action happening outside a dive. **Why:** duel shake tiers are calibrated for HP/turn-loss stakes; reusing the class at full window/desktop scope for a zero-cost desktop action would overstate its importance. **How to apply:** for any future desktop/OS-chrome payoff (not a duel event), reuse the existing shake CLASSES verbatim but scope them to the smallest meaningful wrapper, never `.kp-os-desk` or `.kp-fw`.

- **CSS keyframes that animate an SVG-only property (e.g. `stroke` in `kp-legal-pulse`) cannot be reused as-is on HTML elements.** `kp-legal-pulse` (styles.css ~1757) only touches `stroke`, which no-ops on a `<button>`/`<div>`. When a new DOM (non-SVG) element needs the same pulsing "legal target" language the board already established, write a sibling keyframe with the identical timing/cadence (1s steps(2), same opacity swing 0.5→0.15) but targeting `border-color` instead, and say so explicitly rather than silently claiming reuse. **Why:** claiming "reuse existing keyframe" when the property target differs is a silent bug waiting to happen at integration. **How to apply:** before citing an existing keyframe as reusable on a new element, check whether the animated CSS property actually applies to that element's tag/rendering context (SVG stroke/fill vs. HTML border/background).

- **Touch fallback for a new drag interaction: reuse the OLD proven click/tap flow verbatim rather than attempting a touch-adapted drag.** `setPointerCapture` routes all subsequent pointer events to the captured element, so hover/hit-testing of elements underneath a touch drag requires manual `elementFromPoint` polling every move, which is fragile on touchscreens. Decision: branch by `pointerType` (mouse/pen with >6px movement = live drag; touch, or a mouse/pen release under 6px, or any keyboard activation = the existing select-then-pair-then-confirm state machine PouchCard already shipped). This also fixes keyboard accessibility for free (Enter/Space fires the native click event, which the tap path already handles) and fixes a real existing bug: today's click flow silently no-ops when tapping an illegal partner. **Why:** don't build fragile new touch-drag code when a proven, accessible click flow already exists and can be the fallback; use the redesign as an excuse to close a silent-feedback gap ("silence is a bug") in the process. **How to apply:** any future ui-spec introducing pointer-drag on a touch-reachable surface should default to this same branch-by-pointerType-and-movement-threshold pattern, with the tap path also serving keyboard users.
