- **A persistent diegetic image that must survive across many different content items (per-file, per-entry, per-customer) needs a diegetic role that is NOT "illustrates the current item".** DAD.LOG reuses the single banked `solder-bench-*` dither across 10 very different documents (a will, a neurocare bill, a soldering memory). Framing it as "illustrating whichever file is open" would be a category error the moment a bill is open. Fix: give the image a role that is true of the WHOLE VOLUME regardless of which file is open (here: "the recovery tool's own SOURCE MEDIA preview", the same reason a disk-imaging utility shows a thumbnail of the physical drive it's reading) and make that role checkable by construction, the image renders once and never changes when the per-item content changes (only when the deliberate hue/dither demo control is used). **Why:** this is the concrete difference between "showing the drive" and "showing the document", and it's exactly the kind of diegetic claim the Loremaster gate is asked to verdict, so it needs to be falsifiable, not just asserted in prose. **How to apply:** whenever one banked/budget-zero image must sit next to a list of varied per-item content, look for a frame where the image is true of the CONTAINER (the medium, the source hardware, the tool itself) rather than the currently-selected content, and make "does it change when the selection changes" a literal acceptance check.

- **A "watch it happen" beat (opening/mounting/loading something) reads as diegetic when it has two distinct phases with different endings, not one delay.** DAD.LOG's recovery beat types `recoveryBeat[0]` ("READING SEGMENT...") for every row click, then branches: an unlocked file swaps to `recoveryBeat[1]` ("RECOVERY COMPLETE. FILE MOUNTED.") with its own sfx (`segmentMount`) before the document types in, while a damaged/locked row collapses straight from line 1 into its own fixed "still damaged" content with a different sfx (`segmentDamaged`) and no success line ever appearing. **Why:** if both paths played the same "loading then success" beat, damaged rows would be lying (implying they mounted when they did not); the fork itself is what sells that the tool is actually reading something and honestly reporting what it found. **How to apply:** for any future "accessing/mounting/scanning" beat with both a success and an incomplete/blocked case, give each its own distinct ending line and its own sfx rather than reusing one generic loading spinner for both, and never let the "success" sfx or line fire on the blocked path.

- **When an existing dimmed/locked treatment would bury a line the Tutorial gate needs legible, deviate from the shipped CSS explicitly rather than accepting the inherited dimming.** The old `.kp-jentry-locked` treatment (windows.css:400-403) dims ALL locked body text to `--ch-dim`, but DAD.LOG's damaged-file body carries the diegetic "more diving recovers more" teach, which must not read as throwaway flavor text. Fix: keep that one line's color at full ink while still dimming the surrounding title/provenance chrome, and say so explicitly as a named deviation with the reason, rather than silently inheriting the old class or silently overriding it without comment. **Why:** an inherited dim-everything treatment is exactly the kind of tier-0 legibility bug the Tutorial Agent is watching for; the fix is one CSS scope decision, but it only happens if it's called out by name against the specific gate concern. **How to apply:** whenever a "locked/incomplete" content state carries a line that is doing real teaching work (not just flavor), audit whatever existing dim/disabled treatment would otherwise apply to it and carve out that one line explicitly.

- **ROUND 3 REVERSAL, kept as a lesson not just a fact: a "one persistent container-level image" ruling can be OVERTURNED by a budget/user decision, and when it is, the fix is not "delete the old idiom", it's "give every case, including the now-common NO-IMAGE case, the exact same footprint."** The addendum superseded the SOURCE MEDIA plate (bullet one above) with per-entry attachments once the user approved a 20-credit batch; four of ten cases (the LOG/QUERY files plus the damaged teaser) still get NO image at all. The fix reused card.html's existing bracket-only `.cell-open`/`kp-frame-ticks` idiom plus the existing `.kp-piece-hole` dashed-hole language, scaled to the same 304x304 footprint as every image cell, rather than inventing new empty-state chrome or letting the column shrink/reflow when a text-only file is open. **Why:** "mixed presence is the point, an archive is heterogeneous" (the user's own framing) only reads as intentional if the no-image case is dressed as deliberately as the image case and never causes layout shift; an empty div where an image used to be reads as broken, not as a diegetic claim. **How to apply:** whenever a "some items have art, some don't" situation is approved, budget equal design attention to the ABSENT case (a dedicated empty-state cell reusing an existing bracket/dashed idiom, fixed to the same footprint) as to the present case, and say the footprint-equality explicitly as an acceptance check, not just a visual intention.
- **A single generation-budget approval can make one demo-rig control (here, the Dither HEAVY/FINE/BAYER row) stop applying uniformly across a page.** Once only the reused solder-bench asset has three banked variants and five new commissions ship FINE-only (one post-pass each, to conserve credits), the Dither row visibly does nothing to five of six image cells. **Why:** a demo control that looks page-wide but silently only affects one element is exactly the kind of thing that reads as a bug during a walkthrough. **How to apply:** when a budget decision leaves a rig control's scope narrower than its own label implies, say so explicitly in the spec and add an acceptance check for the narrowed scope, rather than letting it be discovered as a surprise.
