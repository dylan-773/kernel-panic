- **Crop, don't scale, a 1-bit dithered raster that needs to display smaller than its native size.** The house rule (loadout/NOTES.md) is "one dither dot = one CSS pixel"; even a half-scale display (152px of a 304px asset) documented dissolving into checker noise. When a layout wants a small thumbnail/monitor-inset version of an existing dithered PNG, keep the `<img>` at its full native intrinsic width/height (zero resampling) and put it inside a SMALLER `overflow:hidden` container, positioning the image with a negative offset to select a crop window. This reads naturally as "a security monitor showing a fixed zoomed framing" rather than "a shrunk wide shot," so the diegetic justification is often stronger, not weaker. If a genuinely small footprint needs a WIDE field of view (not just a crop), that requires a real new art order at the target size, since no CSS technique substitutes for a fresh dither pass; don't try to fake it by scaling an existing asset down.
- **Use container query units (cqi/cqw), not vw, for type/element sizing inside anything that is "a window on a desktop" rather than "the page."** vw ties size to the outer browser viewport; a window's own tile width is the thing that should drive its internal type scale when the desktop supports multi-window tiling at arbitrary widths, since two differently-sized tiled windows at the same browser width should NOT share a type scale. Establish `container-type: inline-size` on the window's content wrapper (and optionally nest a second container on a sub-panel, e.g. a hero-numeral card, so its own clamp() resolves against ITS column width instead of the whole window). This is the deeper, root-cause fix for "doesn't scale well to other aspect ratios or resolutions" complaints, not just "add more clamp() calls."
- **A hard body-copy floor (e.g. this system's VT323 19-21px) can still be expressed as a clamp(), just a narrow one that never leaves the legal band** (`clamp(19px, 1cqi + 17px, 21px)`), rather than pinning a flat value. This keeps every type rule nominally fluid/consistent with a "fluid rule set" mandate while still honoring a stated floor.
- **When a brief names an explicit narrow-width threshold (e.g. "narrow (<=760px)"), look for an existing system width token that equals it exactly** (here, `--kp-win-w-standard` is literally 760) and assign that token to one of the required demo viewport/checkpoint buttons, so the "hardest case" checkpoint doubles as the literal threshold proof instead of needing a fifth ad hoc button.
- **VIEWPORT-style demo rigs simulating different screen aspect ratios should use REAL representative resolutions (e.g. 1366x768, 2560x1080), not resolutions artificially shrunk to fit a comfortable demo-page width.** Shrinking a stage's absolute size to keep the demo page narrow silently distorts short-but-wide ratios (ultrawide) into implausibly short stages that make an otherwise-fine layout look broken. It's fine, and consistent with the existing "outer page may scroll" allowance, to let selecting a wide ratio (21:9) make the demo page require horizontal scroll.
- **Extreme scale contrast forces real content triage, not just bigger numbers.** For LOADOUT.CFG, committing to "one hero numeral is the biggest thing on the page" required first identifying and cutting the least information-dense original element (a schematic plate photo) entirely, rather than shrinking everything proportionally. When a maximalist brief asks for one dominant focal element per zone, the design work is mostly in the cutting, and the scale-up is what's left after.

See also [[kpos-dither-asset-conventions]] for the underlying dither-cell sizing rules this builds on, and [[ux-agent-proposal-house-style]] for how these get written into a proposal (this cycle's proposal used named structured fields - zones/cuts/fluid/crt/amber/choreography/owedCopy - alongside the usual dense `spec` prose, at a coordinator's explicit request; both forms are acceptable, match whichever the requester asks for).
